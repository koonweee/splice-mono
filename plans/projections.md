# Projections

## Status

Implemented (V1)

## Goal

Add a Projections feature where users can ask natural-language financial projection questions and receive an interactive, editable projection view. The first implementation should support both whole-net-worth scenarios and focused scopes such as account groups or specific retirement/brokerage accounts.

The LLM should have freedom to query the user's financial context and compose a native Splice UI from a safe typed render spec. It must not generate React code, mutate data, or own final financial calculations. Numeric projection results must come from deterministic application logic.

Settled product decisions:

- Projection scope must be flexible enough for net-worth-wide and account/account-group-specific questions.
- Do not persist saved scenarios in V1. Keep generated scenarios in route/component state or query cache only.
- Use OpenAI on the backend with `OPENAI_API_KEY` and the official Node/TypeScript SDK.
- Reuse the existing MCP tool shapes and safety guidance as the design reference, but do not route the web app through the MCP transport unless a later milestone explicitly needs that.

## Current Behavior

- `frontend/src/lib/balance-utils.ts` computes net worth from `BalanceQueryPerDateResult[]`, separates assets/liabilities, creates chart points, and formats dashboard data for `NetWorthCard`.
- `frontend/src/components/NetWorthCard.tsx` renders the current net-worth summary and uses `frontend/src/components/Chart.tsx`.
- `frontend/src/components/Chart.tsx` wraps Mantine `AreaChart` for simple historical area charts.
- `frontend/src/components/analysis/AnalysisSankeyChart.tsx` already uses Recharts directly when Mantine Charts is not flexible enough. Projections should use Recharts directly for historical/projected line separation, confidence bands, custom annotations, and scenario mini-charts.
- Authenticated routes live under `frontend/src/routes/_authed/*.tsx`. Add the new page as `frontend/src/routes/_authed/projections.tsx` and add a nav item in `frontend/src/routes/_authed.tsx`.
- Shared theme and component defaults live in `frontend/src/lib/theme.ts` and `frontend/src/styles.css`. Reuse Mantine `Paper`, `Grid`, `Stack`, `SegmentedControl`, `Slider`, `NumberInput`, `Badge`, `ActionIcon`, `Textarea`, `Tooltip`, and existing formatting helpers from `frontend/src/lib/format.ts`.
- Backend balance history is served by `backend/src/balance-query/balance-query.controller.ts` and `backend/src/balance-query/balance-query.service.ts`.
- `backend/src/balance-query/balance-history-surface.service.ts` already exposes a summary-friendly balance history surface with net worth, chart data, assets, and liabilities.
- Backend API schemas are Zod-first and registered for OpenAPI through `backend/src/common/zod-api-response.ts`. Controllers use `ZodValidationPipe`.
- Frontend API clients under `frontend/src/api/**` are generated by Orval and must not be hand-edited. Run `cd frontend && yarn orval` after backend API contract changes.
- Existing MCP code in `backend/src/mcp/mcp.service.ts` has projection-relevant tools: `get_user_context`, `get_accounts_snapshot`, `get_balance_history`, `list_balance_snapshots`, `get_cashflow_analysis`, and transaction/cashflow drilldown tools. Its guide already says projections should use account snapshots and balance snapshots, and should ask for future assumptions rather than inventing them.
- There is no OpenAI dependency or existing LLM service in `backend/package.json`.
- There is no holdings/security-level investment model. Investment context is currently account-balance-level, with account types/subtypes such as brokerage and 401k.

## Target Data Shape

Add shared projection schemas in `backend/src/types/Projection.ts`. Mirror the frontend render/runtime types in `frontend/src/lib/projections/schemas.ts` unless generated API types are sufficient for a given milestone.

Core scenario shape:

```ts
type ProjectionScope =
  | { kind: 'netWorth' }
  | {
      kind: 'accountGroups'
      accountGroupings: Array<'cash' | 'credit' | 'investment' | 'liability'>
    }
  | {
      kind: 'accounts'
      accountIds: string[]
    }

type ProjectionScenario = {
  id: string
  title: string
  prompt?: string
  currency: string
  startDate: string
  scope: ProjectionScope
  horizonYears: number
  cadence: 'monthly' | 'yearly'
  parameters: {
    currentValue?: number
    annualContributions: Array<{
      id: string
      label: string
      amount: number
      currency: string
      target: ProjectionScope
      startDate?: string
      endDate?: string
      inflationAdjust?: boolean
    }>
    expectedAnnualReturn: number
    inflationRate: number
    taxDragRate: number
    volatility: number
  }
  assumptions: ProjectionAssumption[]
  controls: ProjectionControlSpec[]
  annotations: ProjectionChartAnnotation[]
}
```

Typed UI/render spec:

```ts
type ProjectionAssumption = {
  id: string
  label: string
  valueLabel: string
  source: 'user_prompt' | 'llm_inferred' | 'default' | 'system'
  confidence?: number
  parameterPath?: string
}

type ProjectionControlSpec =
  | {
      kind: 'currencyAmount'
      id: string
      label: string
      parameterPath: string
      currency: string
      min: number
      max: number
      step: number
    }
  | {
      kind: 'percentageSlider'
      id: string
      label: string
      parameterPath: string
      min: number
      max: number
      step: number
    }
  | {
      kind: 'segmentedSelect'
      id: string
      label: string
      parameterPath: string
      options: Array<{ label: string; value: string | number }>
    }
  | {
      kind: 'toggle'
      id: string
      label: string
      parameterPath: string
    }

type ProjectionChartAnnotation = {
  id: string
  kind: 'milestone' | 'assumption' | 'contribution' | 'risk'
  label: string
  description?: string
  date?: string
  value?: number
}
```

Deterministic engine output:

```ts
type ProjectionResult = {
  scenarioId: string
  currency: string
  points: Array<{
    date: string
    historical?: number
    projectedMedian?: number
    projectedLow?: number
    projectedHigh?: number
    totalContributions: number
  }>
  metrics: ProjectionMetric[]
  milestones: ProjectionMilestone[]
  annotations: ProjectionChartAnnotation[]
}

type ProjectionMetric = {
  id: string
  label: string
  value: number
  formattedValue: string
  description?: string
}

type ProjectionMilestone = {
  id: string
  label: string
  targetValue: number
  reachedAt?: string
}

type LLMProjectionPlanResponse = {
  version: 1
  assistantMessage: string
  scenario: ProjectionScenario
  followUpQuestions: string[]
  warnings: string[]
}
```

Zod schema requirements:

- Use discriminated unions for `ProjectionScope` and `ProjectionControlSpec`.
- Clamp horizon, return, inflation, tax drag, volatility, and contribution ranges in backend validation, even when OpenAI Structured Outputs already returns schema-shaped data.
- Keep parameter paths constrained to known prefixes such as `parameters.expectedAnnualReturn`, `parameters.inflationRate`, and `parameters.annualContributions.<id>.amount`; do not accept arbitrary object paths.
- Store money values in major units inside projection scenario/result types because projections are analytical outputs, not ledger records. Convert only at API boundaries if a future persistence model needs smallest units.

## Proposed Architecture

### Backend

Add a new projection module:

- `backend/src/projection/projection.module.ts`

Register `ProjectionModule` in `backend/src/app.module.ts`.

The module should import:

- `AccountModule` for account snapshots through `AccountsSurfaceService`.
- `BalanceQueryModule` for `BalanceHistorySurfaceService`.
- `TransactionAnalysisModule` for cashflow context when needed.
- `UserModule` for timezone/currency/user context.

OpenAI integration:

- Add `openai` to `backend/package.json`.
- Read `OPENAI_API_KEY` only in backend code.
- Create an OpenAI client in `ProjectionLlmService`.
- Use the Responses API with Structured Outputs and the SDK Zod helper so `LLMProjectionPlanResponseSchema` is the source of truth.
- Use a hardcoded backend model constant for projection planning: `gpt-5.4-mini` with reasoning effort `xhigh`.
- Treat refusals, schema failures, missing API key, and OpenAI errors as recoverable API errors with stable frontend messages.

Internal tool model:

- Add `ProjectionContextService` methods that mirror MCP tool shapes without using MCP transport:
  - `getUserContext(userId)`
  - `getAccountsSnapshot(userId)`
  - `getBalanceHistory(userId, input)`
  - `getCashflowAnalysis(userId, input)`
  - `listBalanceSnapshots(userId, input)` only if the first LLM flow needs raw snapshots.
- Give the LLM access to these as OpenAI tools or as explicitly supplied compact context, depending on implementation complexity. Prefer tools once there is more than one optional data source to avoid sending unnecessary private data.
- Keep these query tools read-only.
- Add a deterministic `computeProjection(scenario, context)` tool or service call, but do not let the LLM author final metric values.

Endpoints:

- `POST /projection/plan`
  - Body: `{ prompt: string; currentScenario?: ProjectionScenario; historyWindowYears?: number }`
  - Behavior: gather minimal context, let OpenAI infer a scenario and UI spec, validate/clamp, compute projection, return plan plus result.
- `POST /projection/compute`
  - Body: `{ scenario: ProjectionScenario }`
  - Behavior: validate/clamp and compute deterministic output without an LLM call.

Do not add saved-scenario CRUD or migrations in V1.

## Overall Exit Criteria

- Users can open `/projections`, ask a natural-language projection question, and receive a typed interactive projection view.
- The LLM can query relevant user context and choose an appropriate scenario scope and render spec.
- The frontend only renders known typed UI spec components.
- Editing generated controls recomputes deterministic projections without an LLM call.
- Final numeric outputs, chart points, confidence ranges, summary metrics, and milestones are computed by `ProjectionEngineService`.
- No saved-scenario persistence, database migration, or user-owned scenario CRUD is included in V1.
- Financial assumptions are visible as pills/controls, projected values are rounded appropriately, and a concise disclaimer is shown.
- Backend and frontend targeted tests, lint, typecheck, API generation, and browser validation pass.

## Risks And Open Questions

- OpenAI model choice is intentionally hardcoded to keep scenario planning behavior stable. Revisit the backend constant deliberately when changing models.
- The current app has account-balance-level investment data, not holdings/security-level data. Prompts mentioning specific ETFs such as VWRA should map to return assumptions, not actual holding lookups, until holdings exist.
- Confidence bands in V1 are deterministic approximations, not Monte Carlo. Label them as ranges/estimates and avoid implying statistical rigor beyond the implemented method.
- Tool-based LLM context can expose more private data than needed. Start with minimal context and tool descriptions that encourage targeted reads.
- Parameter-path rendering is powerful but risky. Keep an allowlist and tests so LLM-generated controls cannot update unrelated scenario fields.
- Recharts annotation labels can collide on small screens. Mobile should degrade to visible assumption/milestone lists below the chart when labels cannot fit cleanly.
